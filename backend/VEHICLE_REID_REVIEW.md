# 双摄像头车辆跨镜重识别：分析与实测

日期：2026-09-29。范围：车辆视觉特征、车辆在线关联、离线验收。

**当前不能宣称“15 张截图和两段视频 100% 跨镜识别”。**
检出目标、检索到正确图片、连续视频保持正确全局 ID，是三个不同指标。

## 1. 数据与验收口径

- 所有 15 张原始截图均运行汽车/货车检测，左右画面分开，自动去除 VLC 标题栏、黑边、播放控制栏，共 30 个视图。
- 六张“同一辆车”截图提供六个明确的汽车/货车正样本对，共 12 个目标框。人工框只用于评价和参考裁剪，不参与生产检测与关联决策。
- 另外九张截图涉及行人、骑行者；本次只做画面内汽车/货车检测冒烟检查，没有进行私人个体跨镜身份匹配。这九张不能算作已通过身份重识别测试。
- 六组车辆构造 6×6 检索矩阵，包括 6 个正对、30 个异车负对。正反两个方向分别统计 Rank-1；另统计分数阈值、分差与双向最佳约束下的确认数。
- 漏检保留在分母内。不同标注车辆复用了相同 Global ID，计为碰撞；两边有 ID 或出现同一个 ID，本身不代表识别正确。
- 原视频分别为 3615 帧 / 20 fps（180.75 秒）、4546 帧 / 25 fps（181.84 秒），均为 2560×1440。
- 全视频时间范围以每路 2 fps 抽样推理，额外加入 12 个标注帧，合计 735 个推理帧。**不是对全部 8161 帧逐帧推理，也没有全部目标的身份真值。**
- 视频配对正确数检查连续运行到六组标注时刻的输出，以及这六个身份之间是否混用 ID；不等价于逐帧 IDF1、HOTA 或全视频每辆车均正确。
- 截图对应视频帧通过同一路画面的像素误差搜索定位（VLC 时间前后各 2 秒），不使用 ReID 分数挑选“正确”轨迹；定位误差、源帧号、框与 IoU 写入 JSON。
- 两视频起点差按文件名暂取 2 秒。这是可修改的时间对齐假设，尚未完成相机时钟与几何标定。
- 测试不启动 Flask 应用、不修改业务数据库、不调用 OCR、不上传媒体、不加载人员特征模型。

## 2. 关键发现

### P1：模型名称不能证明模型内容

本地 `transreid.onnx` 输入是 1×3×256×128，图中实际含 ResNet/IBN 卷积层。
这与目录及后台显示的“TransReID / ViT”描述不一致；无法仅凭文件名确认训练集和车辆专用训练来源。

`clip_vehicle_reid.onnx` 与 `vehicle_vit_reid.onnx` 的 SHA-256 完全相同，均为：

`38d295c5c462877ca1e1e3fa3219557cc2a398c24cc7f15d53d840c5b5c05e53`

二者不是两种独立模型，不能把它们的结果当作独立模型投票。

旧 `transreid.onnx` 的 SHA-256：

`6c99a68393454a4b3c03d5fe8410040ee4ca34c2c15e062af4d74c7cda12155d`

### P1：在线车辆绑定时间和相机特征没有随观测更新

车辆引擎在命中 sticky 绑定后直接返回 Global，绕过关联器的观测更新。
局部轨迹持续存在时，`last_seen`、该镜头的观测时间与原型仍可能停在首帧。
复现测试中，同一车辆在 100、101.5、103 秒连续出现，原实现产生了两个 Global ID。

已增加车辆专用绑定刷新：只刷新原有绑定，不搜索新身份；采样帧更新相机原型，跳过特征提取的帧仍更新占用时间。候选状态不会因此晋升为确认身份。

### P1：目标在画面中的大小被误当作真实车型

原逻辑会把占画面面积超过 10% 的已检测 `car` 强制改为 `truck`。
同一汽车在近镜头变成货车、远镜头仍是汽车，随后被跨镜类别冲突规则拒绝。
已保留检测器明确给出的汽车/货车/客车类别。

### P1：ByteTrack 适配层重复晋升临时 ID

原生 ByteTrack 已确认轨迹的 ID，在适配层每一帧仍被重新匹配到最近的临时框。
这会使两车交叉时交换 ID，也可能使后来的新车继承前车 ID。两个确定性车辆测试在原代码上均失败。
现将原生 ID 到局部 ID 的晋升固定为一次映射，晋升后移除可被复用的临时框；同一帧的临时 ID 也保持互斥，并在轨迹超期时释放映射。

进一步的视频日志显示，镜头 71 的临时 ID `900008` 在相对时间 30.20 秒最后出现，又在 38.50 秒被另一辆车复用。未确认的检测框没有原生身份依据，不能按已确认轨迹的 30 帧宽限期跨越检测中断。因此临时框只允许续接相邻观测；已确认原生轨迹仍由跟踪器管理遮挡与恢复。两项中断复用测试也完成了先失败、后通过的验证。
这是单镜局部跟踪 ID 的修复，没有增加人员身份特征或人员跨镜匹配规则。

### P1：局部跟踪激活阈值被库的默认分流阈值覆盖

本机 `trackers==2.6.0` 的 ByteTrack / BoT-SORT 只为高置信度分组创建新轨迹。
项目设置激活阈值 0.25，却未设置高低分流阈值，后者默认 0.60。
结果是持续出现、置信度 0.45 的车辆检测永远只有 `tracker_id=-1`，只能依赖临时 IoU 框。
两个真实库集成测试均先复现失败；现将高低分流阈值显式对齐配置的激活阈值，两个后端均可确认这类车辆轨迹。低于激活阈值的检测仍可参加已存在轨迹的低分恢复阶段。

### P2：特征空间、输出和资源管理存在缺口

- 原空间版本只使用 ONNX 文件名；不同目录、不同版本的同名权重可能混在一起。现使用权重 SHA-256 区分车辆特征空间。
- 原输出没有拒绝 NaN、Inf、空向量、零向量或错误批次。现标记降级原因，避免把无效数值作为正常 ONNX 特征。
- 原额外输入统一使用形状 `(1,)` 和 int64；现遵循模型声明的形状和 dtype。
- 原 ONNX 会话缓存按 mtime 永久累积。现移除同路径旧版本，并限制最多四个缓存会话。
- 原直方图使用像素计数，而边缘/亮度是统计量，目标分辨率变化会改变两者权重。现按像素数与数值范围归一化，并升级备用特征空间版本。

### P2：环境与验收脚本问题

- 项目 `.venv` 指向已失效的 Python312 路径；本次使用可用的 Anaconda Python / PyTorch CPU / ONNX Runtime CPU。
- 初始环境缺少已列在 requirements 中的 `trackers`，实际回退到 IoU；随后在项目隔离目录安装 `trackers==2.6.0`，复测真实 ByteTrack。
- 本机出现 OpenMP 运行库冲突。测试命令使用 `MKL_THREADING_LAYER=SEQUENTIAL`，没有采用允许重复 OpenMP 运行库的危险绕过方式。
- 旧评估报告的“关联率 100%”是分配 ID 的比例；还包含负持续时间。新增基准使用有标注的配对正确性、异车负对和 ID 碰撞。

## 3. 截图实测

检测器 YOLO26n，输入 640，检测置信度 0.28；汽车/客车/货车类别 2、5、7。
自动框检出按 IoU ≥ 0.5 判断。六组目标共 12/12 被检出；并不意味着背景所有车辆也有 100% 检出率。

| 指标 | 原 transreid 文件 | CLIP 车辆 FP32 |
|---|---:|---:|
| 六组目标检出 | 12/12 | 12/12 |
| 人工参考框 Rank-1，71→81 | 2/6 | 6/6 |
| 人工参考框 Rank-1，81→71 | 1/6 | 6/6 |
| 自动框 Rank-1，71→81 | 2/6 | 5/6 |
| 自动框 Rank-1，81→71 | 1/6 | 6/6 |
| 自动框保守确认正确数 | 0/6 | 5/6 |
| 自动框保守确认错误数 | 0 | 0 |

原模型确认阈值 0.48、分差 0.04；CLIP 评估阈值 0.80、分差 0.04。
CLIP 自动框仍有一个异车负对超过 0.80，说明只按单一阈值判断会误配。
主要混淆是样本 car01 与 car04 两辆黑色轿车。

人工参考框的 6/6 只属于这六个已知配对的闭集检索，**不是自动端到端 100%**，也不是独立留出集上的泛化准确率。

## 4. 视频实测

完整结果见 `uploads/vehicle_benchmark/` 下各轮的 `report.json` 和逐帧 `video_frames.jsonl`。

| 运行 | 范围 | 正确且未与其他标注车辆混用 ID |
|---|---|---:|
| baseline_video | 原模型 + 原车辆逻辑 + IoU 回退，735 帧 | 0/6 |
| final_video | CLIP FP32 + 本轮修复 + IoU 回退，735 帧 | 1/6 |
| bytetrack_video | CLIP FP32 + 原 ByteTrack 适配层，735 帧 | 2/6 |
| fixed_tracker_video | CLIP FP32 + 一次晋升修复，735 帧 | 1/6 |
| final_gap_video | 增加未确认 ID 相邻观测限制，735 帧 | 0/6 |
| final_activation_video | 最终代码 + CLIP FP32 + 对齐激活阈值 + ByteTrack，735 帧 | 0/6 |
| final_default_video | 最终代码 + 原默认模型 + ByteTrack，735 帧 | 0/6 |

IoU 路径下白色 SUV（car02）正确关联；car03 与 car04 仍共享了错误 ID。
原 ByteTrack 适配层的 car03、car04 正确关联，但 car01 与 car02 发生 ID 混用，促成了上面的适配层修复。
一次晋升修复仍存在未确认 ID 跨越检测中断复用的问题（car01 与 car02），最终增加了相邻观测限制。
相邻观测限制后，六个标注身份之间的 ID 碰撞消失，但轨迹碎片增加，暴露出上面的激活阈值问题。中间实验结果全部保留，没有只选最好的一次。

最终 CLIP 视频复测为 **0/6**，car03 与 car04 仍复用了同一 Global ID。12 个标注框均检出，735 帧运行未记录帧处理异常，但这些不能算作重识别成功。最终代码解决了确定性缺陷，**尚未证明连续视频身份关联准确率提高，不应按“识别率优化完成”验收**。

最终默认模型视频复测也为 **0/6**，六个标注身份之间没有发现 ID 碰撞，但同车仍被分成不同 Global ID。默认模型运行 179.94 秒，帧处理均值 190.69 ms，P95 240.81 ms；无帧处理异常。不同运行的机器负载未严格控制，因此不把相对原始 239.41 秒的耗时差宣称为代码加速比。

原因链中仍未解决的部分：进入画面时的早期单视角特征已经新建/绑定了不同 Global ID，后面的近景高质量特征主要用于更新该绑定；它不会自动纠正所有历史错误合并或分裂。代码中的候选确认、占用约束和图库更新需要结合轨迹真值评估，不能以图片闭集检索替代。

这些指标仅覆盖六个标注对象；其余检测目标缺少跨镜真值，不能据此声称完整视频精确率达到 100%。

## 5. 性能与未采用的实验

- 同一批 12 个自动目标裁剪，原模型热推理均值约 155 ms；CLIP FP32 约 390 ms。模型替换提高了检索准确率，但单次特征提取更慢。
- 第一种动态 INT8 导出从 345,338,011 字节减少到约 89,986,047 字节，但检索准确率显著下降；缩小量化范围后仍未恢复 FP32 的可靠性。两个实验权重均未替换现有模型。
- 去除裁剪边缘上下文的实验未改善自动框 Rank-1，也未保留为生产改动。
- 静态裁剪相似缓存在两个完整视频测试中均为零命中，已从最终代码移除。
- 在线模型会话改为有界缓存，避免长期切换权重版本时内存持续累积。
- 已确认原生 ID 的适配从每帧扫描临时框改为字典查询；这是局部算法改进，不代表整条推理链已实现实时处理。
- 最终 CLIP 双视频抽样运行：735 帧，342.79 秒；帧处理均值 393.62 ms，P95 812.35 ms。当前 CPU 环境尚不满足两路各 2 fps 的持续实时处理要求。该结果包含启动与解码开销，也受到本机测试负载影响。
- 墙钟耗时受当前 CPU 与并行测试负载影响；跨不同模型、不同负载的墙钟时间不能当作纯代码加速比。

## 8. 复现方式

在项目根目录，以可用 Python 运行。输出目录必须位于本机，不需要上传视频。

```powershell
$env:MKL_THREADING_LAYER = 'SEQUENTIAL'
# 本次隔离安装的已声明依赖；标准部署应安装 backend/requirements.txt。
$env:PYTHONPATH = "$PWD/backend/.tmp_reid_deps"
python backend/scripts/benchmark_vehicle_reid.py `
  --stage all `
  --output backend/uploads/vehicle_benchmark/reproduce `
  --reid backend/uploads/models/base/clip-reid-vehicle/clip_vehicle_reid.onnx `
  --threshold 0.8 --margin 0.04
```

基准脚本的参数会写入 JSON。默认时钟差 2 秒、采样率 2 fps、原型预算和模型均明确记录。
CLIP 在基准中显式指定；由于连续视频收益不足以支撑全局切换，未改变业务默认模型优先级。
业务会话已有的阈值配置不自动改写，本次测试阈值不能被理解成所有场景通用阈值。

复现默认模型的最终对照：沿用上述环境变量，执行：

```powershell
python backend/scripts/benchmark_vehicle_reid.py `
  --stage videos `
  --output backend/uploads/vehicle_benchmark/reproduce_default `
  --reid backend/uploads/models/base/transreid-vehicle/transreid.onnx `
  --threshold 0.48 --margin 0.04
```

主要产物：

- `scripts/benchmark_vehicle_reid.py`：离线基准，人工标签只参与评价。
- `uploads/vehicle_benchmark/clip_fp32/report.json`：15 张截图与六组车辆检索矩阵。
- `uploads/vehicle_benchmark/final_default_video/report.json`：最终默认模型视频结果。
- `uploads/vehicle_benchmark/final_activation_video/report.json`：最终 CLIP 视频结果。
- 每轮输出目录下的 `video_frames.jsonl` 和 `video_<camera>_<case>.jpg`：逐帧输出与标注帧。
- `uploads/vehicle_benchmark/final_activation_gate.log`：76 通过、1 跳过的验证日志。
- `uploads/vehicle_benchmark/mtmc_suite.log`：更广回归的两项失败详情。

`uploads` 被仓库忽略，上述实测产物保留于本机；基准脚本、测试与本报告可纳入版本控制。

## 10. 本轮交付边界

交付代码修复、失败复现、可复跑基准和实测报告。未达到 100% 识别，也未通过连续视频识别率提升验收。
临时 ID 的相邻观测限制会增加未确认轨迹在漏检后的碎片，这是避免不同车辆误继承 ID 的取舍；需在完整轨迹标注上进一步量化。
车辆权重版本和直方图版本发生变化时，特征空间会明确隔离，旧版本特征不再与新版本直接比对。
后续提高成功率需要可靠的车辆模型来源/输入规范、时钟与路面标定，以及独立的轨迹验证集。当前六组已反复用于诊断，不应作为泛化性能证明。
